## 3. SET 部分写入：规范已直接给出处理原则

### 3.1 已核实的规范

RFC 3416 §4.2.5，印刷页 19–22，明确把变量绑定处理分成概念上的两个阶段：先验证所有变量，全部成功才进行赋值；赋值应表现为同一请求内同时完成。如果赋值阶段仍失败，需要撤销其他赋值并报告相应错误。这是**验证/赋值两阶段**，不是要求引入分布式数据库的“两阶段提交协议”。[1](https://www.rfc-editor.org/rfc/rfc3416.html)

RFC 1157 §4.1.5，印刷页 25–26，同样先列出错误条件，再规定不存在这些错误时才赋值，同一消息中的赋值表现为同时生效。[1](https://www.rfc-editor.org/rfc/rfc1157)

### 3.2 对应当前代码

当前 `snmp_lite.v:522–541` 在逐个 VarBind 的 `P_RESOLVE2` 中就发出 `ctl_we` / `vl_bag_we`。后续变量出错时，前面已经写过。`P_BUILD2` 等状态又在写入之后才处理部分响应长度/tooBig 条件。

因此，**只把写使能移动到“最后一个 VarBind”附近还不够**：所有会拒绝整份请求的可预测条件，都应在产生写副作用之前处理。

### 3.3 建议的 RTL 结构（工程建议，尚未实施）

```text
接收完整请求、锁定上下文
        ↓
无副作用解析 + 响应空间预检
        ↓
校验全部 VarBind：OID / 权限 / 类型 / 长度 / 值 / 资源
        ↓
保存写意图：目标对象、索引、新值、必要的旧值
        ↓
全部通过 → 提交 → 编码响应
任一失败 → 错误响应，零写入
```

- 可围绕当前最多 8 个 VarBind 建立小型写意图表，不必引入处理器或庞大的事务系统。
- 保留首个错误的索引，但不能因为某个较早或较晚对象合法就提前写。
- 提交端若可能因仲裁、资源或状态变化失败，必须设计撤销/恢复；或者通过资源预留、提交互斥和目标限制，证明通过预检后的提交不会失败。
- 主机与 SNMP 并发修改同一对象、复位中止、重复 OID、响应空间不足都要有定义。逐拍写完多个对象不自动等于外部观察上的原子性。
- 提交接口必须确保每笔写被真正接纳，不能用可能被仲裁覆盖的单拍脉冲假定写入成功。

**验证出口：** 合法多变量 SET 全部生效；第一/中间/最后变量出错、过多 VarBind、tooBig、复位等场景不出现不符合契约的部分修改；再验证顶层 CTL/BAG 实际写回。

### 3.4 文献核对还暴露了一个规范差异

设计书和当前 RTL 将 SET 到只读对象统一映射为 `readOnly(4)`。但 RFC 1157 §4.1.5 对其所述“不允许进行 SET 的对象”使用 `noSuchName`；RFC 3416 §4.2.5 又有 `notWritable` 等更细分规则，不能两种版本共用一张简化错误映射表。[1](https://www.rfc-editor.org/rfc/rfc1157) [1](https://www.rfc-editor.org/rfc/rfc3416.html)

RFC 3416 定义的 `notWritable(17)`、`inconsistentName(18)` 超出 4 bit；而当前 `r_err`、部分错误状态/观测接口使用 4 bit。**若继续按项目声明支持 v1/v2c，应复核错误码、位宽和主机观测字段，而不是只替换一个常量。**[1](https://www.rfc-editor.org/rfc/rfc3416.html)

上轮隔离探针检查错误码 4，是为了识别并复现**旧实现的失败路径**，不是认定 4 就是规范要求。后续应按冻结后的版本语义更新合规 oracle，同时保留旧失败原件。本项为规范/代码对照发现，本轮未新增动态用例。

## 4. 请求静默覆盖：用有界缓冲与明确的接收契约解决

### 4.1 可以借用的文献原则

项目 L001 / XAPP1130 p.6 有按 VL 的 FIFO 与顺序管理描述；p.13、p.18 给出软硬件分层、packet FIFO 和处理器承接管理功能的示例。对应项目文本 `_xapp1130_text.txt:608–628, 1064–1091, 1295–1306`。这些支持“职责分离、缓冲解耦”，**没有给出本项目必须使用多少个 SNMP 请求槽位**。

作为具体内部握手的方法参考，ARM IHI 0051A §2.2.1（印刷页 2-3，PDF 第 19 页）规定：有效传输在 valid 与 ready 同时成立时发生；未完成握手时，valid 及关联数据/控制信息要保持。这份规范可用于构造本项目的内部接口契约，但**不是 AFDX 强制要求使用 AXI4-Stream**。[2](https://documentation-service.arm.com/static/60d5e2510320e92fa40b4788)

### 4.2 建议的实现选择

**共同底线：** 正在解析/响应编码的请求不能被新报文改写。请求数据与长度、源端口、源 IP（如需）、request-id 等上下文必须属于同一个请求槽位。

可选择两种明确的策略：

1. **内部背压贯通**：为 SAP→SNMP 增加真实的接纳/保持机制；无空间时暂停内部传输，并保持数据、SOP/EOP 和元数据。不能仅修改 `snmp_lite.in_ready`，因为顶层目前没有使用它。
2. **有界请求缓冲 + 满时整包拒绝计数**：例如两个请求槽位和状态/索引队列；入包时决定是否有容量。满时消费并丢弃完整报文、增加明确的 busy/overflow 计数，不碰活动请求内容，也不把被拒绝的报文记成已入队。

推荐先明确最大在途数量和满载策略，再选最小可维护实现；**增加 FIFO 深度本身不能解决无限期响应背压**。

建议每个槽位具有清晰生命周期：

```text
FREE → FILLING → READY → IN_USE → FREE
```

释放点应是最后一次读取请求内容之后，而非看到 EOP 就释放。当前响应编码会使用请求上下文，因此请求缓冲与响应缓冲的生命周期要分别确定；响应仍需保持到 ACK。

外部以太网接收不能被这个内部 ready 任意暂停。应把内部排队/背压与入口无空闲块时的整帧丢弃分开，不让池耗尽变成覆盖或泄漏。

**验证出口：** 连续请求、长响应背压、队列满、同拍进出、不同源端口、复位中止；每个完整到达报文可归类为已完成、明确拒绝或仍在系统内，不允许静默消失。修改共用 SAP 后还需回归 TFTP 和块归还路径。

## 5. 125 MHz：已有多周期思路，但必须落在真实热点上

### 5.1 项目内就有可复用的设计意图

设计书 `AFDX端系统_总体设计书.md:838` 原本写过“排序 OID 列表、二分查找、7 拍”的 GETNEXT 方案；当前 RTL `snmp_lite.v:260–280` 则主要通过组合的 `idx_of()` / `walk()` / `grp_i()` / `leaf_i()` / `inst_i()` 求解。

这说明**多周期查找不是必须从零发明的新方向**。但文档的“128 项、7 拍”是旧规划，不能直接覆盖当前 MIB 的索引展开和统计对象。必须先从实际支持对象生成/核对完整排序关系及边界。

### 5.2 厂商资料给出的约束

Altera *Recommended HDL Coding Styles*，QII51007（2014-08-18）印刷页 12-10、12-12～12-13，强调同步 RAM、读写同址语义，并说明综合会把读地址或输出寄存器打包进 RAM，必要时增加旁路逻辑。因此，不能仅数 RTL 中有几个 `reg` 就判定已经形成了理想的流水边界。[1](https://people.ece.cornell.edu/land/courses/ece5760/DE1_SOC/HDL_style_qts_qii51007.pdf)

该资料是 Altera 原文的高校镜像，**不是当前 Quartus II 13.0.1 的同版本手册**。本轮只采用同步存储/寄存边界/读写冲突的通用原则；不照搬新版 HyperFlex、Vivado 或特定器件开关。

### 5.3 推荐路线（待实现、待测量）

上轮真实报告的最差 50 条路径集中于：

```text
SNMP oid_len → OID/GETNEXT 求解 → 统计 RAM 地址寄存器
```

所以优先候选为：

```text
OID 与请求上下文锁存
    → 对象/后继索引求解
    → 索引译码、MIB 地址寄存
    → 同步 RAM 读
    → 数据和错误状态锁存
    → 后续事务处理/响应编码
```

- **最小改动路线：** 保留当前对象映射和支持范围，进一步切开已有组合求解链。
- **备用路线：** 从实际 MIB 清单生成排序表，用有界多周期查找替代大组合链；不硬套旧文档的表容量和拍数。
- 每一阶段同时携带操作类型、VarBind 序号、错误状态、写值和有效标记，不能只给数据加拍而让控制来自另一个请求。
- GETNEXT 必须保持所声明 MIB 视图内的词典序后继语义；流水化不是改变 OID 行为的理由。规范入口为 RFC 3416 §4.2.2。[1](https://www.rfc-editor.org/rfc/rfc3416.html)
- 控制面允许增加若干内部周期是设计取舍，不等于可以无依据地给路径加 false path 或 multicycle。
- 配置表 BRAM 化可作为后续资源/热点优化，但不应因为看过存储论文就先重写全部 TX/RX 配置路径。

**验证出口：** 先通过事务、排队、GETNEXT 首尾/跨组/缺失项/背压/复位测试，再保持 8 ns 约束重新 map/fit、多角 STA。增加流水只能提出改善假设，**不能预先保证必达 125 MHz**。

## 6. 两个测试问题不需要再等论文

## 8. 建议下一步

按最小改动组织：**冻结错误/接收契约 → 补失败用例与可靠门禁 → 修事务和缓冲所有权 → 完整功能回归 → 再做 OID/GETNEXT 多周期优化与 post-fit。**

本轮只新增文献核对与设计建议，未修改 RTL、原 TB、原文献目录编号或历史证据，也未声称修复、仿真或时序已经完成。
