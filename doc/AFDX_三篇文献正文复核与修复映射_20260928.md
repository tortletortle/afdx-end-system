## 1. 结论

**三篇原文已经补齐，修复已复现的 SNMP 功能缺陷和测试门禁，不需要再等待更多论文。** 原文使方案更具体，也揭示了不能照搬的地方：

1. **L044 给出了队列、端口控制块和消息长度数组的设计依据，但明确没有完成 SAP 扩展。** 可以借鉴所有权与缓冲组织，不能说它提供了现成的 SNMP/SAP 背压电路。
2. **L074 给出了接收、解析、MIB 操作、缓冲管理和响应发送的分层。** 其“两个阶段”不是 RFC 意义的“所有 VarBind 验证后原子提交”，不能用这句话证明 SET 事务正确。
3. **L071 最适合转成具体的自动化验证工作：激励、期望值、顺序、计数、边界、恢复和报告。** 但个别表格的计数/长度口径有疑点，必须重新推导，不能直接当作黄金判据。
4. **三篇均未给出当前 SNMP RTL 达到 125 MHz 的实现或证据。** 分层思路可迁移为多周期处理，时序结果仍须由修改后的实际综合、布局布线和 STA 给出。

这份复核补上了上一份《文献依据与修复建议》中“三篇中文 PDF 本轮未读”的资料缺口；不改写当时的阅读记录，也不把本轮阅读变成新的 RTL PASS 证据。

## 3. L044：请求不能被当作“最新采样值”覆盖

### 3.1 原文确认了什么

- **§2.1，期刊p.57 / PDF第2页：** 采样端口保留最新消息、允许覆盖和重复读取；队列端口按 FIFO 保存消息，读出后移出。
- **§3.1–3.3，期刊pp.57–58 / PDF第2–3页：** 端口控制块关联数据缓冲与消息实际长度；队列有读写指针。加载配置、创建端口、发送/接收分开。
- **§3.3，期刊p.58 / PDF第3页：** 创建端口时查找外部端口号，运行时通过内部 `portid` 访问相应状态。发送过程先拷贝数据、记录长度并更新指针，再通知硬件。
- **结束语，期刊p.59 / PDF第4页：** 明确写到“目前本方法只是针对AFDX通信端口，下一步要进行SAP端口的扩展”。

### 3.2 能怎样迁移到当前项目

**工程推导，不是论文已有 RTL：**

- 管理请求具有独立的操作与响应，不能用采样端口“最新覆盖”的方式处理；尤其不能覆盖已接纳请求的内容，却继续表示接收正常。
- 每个请求槽位应绑定自己的长度、源信息、解析上下文和状态，而不是多个请求共享一份可任意改写的 `req_len`、`peer_port`、`have_pkt`。
- 明确 `FREE → FILLING → READY → IN_USE → FREE` 的生命周期。报文完整接收后才可发布，最后一次使用请求数据后才可释放。
- 在 RTL 中采用固定容量/参数化的存储与索引，不照搬论文驱动中的动态申请内存、指针或中断 API。
- 可借鉴“外部标识与内部索引分离”，但端口 `portid` 机制不等于已经实现 SNMP 的 GETNEXT。

**文献没有替本项目决定的事：** 请求槽位数量、队列满时丢弃还是背压、并发入队/出队、请求与响应缓冲的释放时刻。这些仍须写成可执行的接口契约并测试。

## 4. L074：能帮助拆模块，不能替代 SET 原子性规范

### 4.1 直接可用的正文依据

| 原文位置 | 原文内容 | 对本项目的作用 |
|---|---|---|
| §2.5.1，pp.12–13 / PDF第20–21页 | RequestID 用于请求/响应匹配；ErrorStatus、ErrorIndex、VarBindList 的用途 | 将响应关联和错误索引纳入请求上下文与 scoreboard，不能只检查“有一份响应” |
| §4.1，pp.29–31 / PDF第37–39页 | Manager/Agent、MIB 与网络访问分工；软件运行于 Windows/VxWorks 环境 | 借鉴职责分层，不照搬操作系统和处理器平台 |
| §4.2.3–4.2.4，pp.33–35 / PDF第41–43页，图4-3、4-4 | 解析、命令处理、MIB 操作、缓冲管理、报文构造和网络发送 | 将接收缓冲、命令上下文、MIB 服务和响应缓冲分成明确阶段 |
| §4.3.2，p.37 / PDF第45页 | 未及时响应时按间隔重试，超限后告警 | 应测试超时/重试与响应关联；不能拿重试机制为静默覆盖请求开脱 |

图4-4 中的不同数据结构和“缓冲管理”模块，支持对逻辑对象及其生命周期进行区分，**不意味着必须把同一个报文物理复制很多份，也不规定 FIFO 深度**。

### 4.2 必须澄清的“两个阶段”

在 **§4.2.4，p.33 / PDF第41页**，论文用“两个阶段”描述 MIB 访问，展开的内容是：

```text
根据变量绑定列表定位 MIB 节点/节点集合
    → 取得并调用相应操作的回调函数
```

这不能直接解释成：

```text
验证整份 SET 的全部变量
    → 全部通过后，原子地提交写入
```

本轮核查的 §4.2 和 §6.1 没有提供足以证明“后一个 VarBind 报错时，前面所有修改均不生效/被恢复”的实现与负例证据。也不能仅凭论文的抽象描述，反过来断言作者的软件一定存在相同缺陷。

**当前项目的 SET 修复仍以 RFC 为规范依据：** RFC 3416 §4.2.5 要求先验证，再在全部通过后赋值；赋值阶段失败需要撤销其他赋值。具体 RTL 可以采用写意图表、资源预留和提交状态机，而不是边解析边产生写使能。[1](https://www.rfc-editor.org/rfc/rfc3416.html)

建议流程：

```text
锁定请求上下文
    → 无写副作用地解析与校验（包括响应容量/tooBig 等条件）
    → 保存整份请求的写意图
    → 全部通过后提交；失败则不提交
    → 形成并保持响应
```

若提交端仍可能拒绝写入，需要可靠的接纳/完成反馈与恢复机制；不能仅假设一个写脉冲一定成功。复位、主机并发配置及重复 OID 的处理也要冻结。v1/v2c 错误语义与现有4 bit字段的限制，仍按上一份文献说明单独处理，不直接复制论文中的简化格式描述。

### 4.3 不把展示性测试当作硬件合规证据

**§6.1，pp.55–58 / PDF第63–66页** 主要展示管理界面、菜单、设备配置、MIB 浏览和告警对话框。本节没有给出本项目所需的多变量 SET 失败原子性、持续背压下请求守恒或 FPGA 时序结果。

论文的错误/结果反馈经过网络访问接口发出，见 **p.35 / PDF第43页**。当前项目的管理响应主要通过主机观测窗读取，因此仍须区分“协议子集处理与观测通过”和“完整线上 Agent 闭环”。

### 4.4 顺带确认：TFTP 不等于完整 615A

**§5.1，p.39 / PDF第47页** 将信息、上传、下载、FIND、协议文件处理与 TFTP 列为不同模块；**§5.2.11，p.52 / PDF第60页** 描述 TFTP 的 Get/Put、超时、重试和终止接口。

可据此组织后续功能分层，但不能用 TFTP WRQ/DATA/ACK 的测试通过替代 615A 上层流程。本轮不因此自动扩大当前修复范围。

## 5. L071：最值得直接吸收的是“步骤—期望—结果”的验证方法

### 5.1 正文中可落实的测试原则

- **§2.2.2，pp.12–13 / PDF第18–19页：** TR-TE 命令/响应流程；复位完成确认后执行规定的操作，并把实际有效载荷与期望值比较。
- **§2.2.4，p.14 / PDF第20页：** 强度/饱和、恢复、输入和状态转换边界测试。
- **§3.2.2，p.18 / PDF第24页，表3-3：** 用递增内容检查 FIFO 顺序，并核对收发计数，而不只是确认收到一条数据。
- **§4.2.3，pp.34–36 / PDF第40–42页：** 用例解析、数据生成、执行、结果分析和数据保存分开，包含计数和状态读取。
- **§4.2.6，p.38 / PDF第44页：** 报告记录环境/版本、用例编号、成功与失败数、失败位置和原因。

**迁移到本项目：** 可以用 Questa 的 BFM/独立参考模型扮演测试端，用 DUT 扮演被测端，不必为了借鉴方法新增 Qt、PCI 板卡或另一套操作系统。仍需加入并发注入与长时间响应背压，不能只保留串行一问一答，否则会再次漏掉请求覆盖。

### 5.2 原文也需要审查，不能照表抄数字

本轮对以下原页做了图像核验，确认并非单纯的文字抽取错误：

1. **表3-4，p.19 / PDF第25页：** 写有“100条长度为8K字节的消息”，期望栏又写“发送帧数计数增加60”。如果后者指全部100条消息的普通数据帧计数，口径不能对齐。以单网、普通无压缩数据帧且帧长不超过1518 B为例，即使不扣帧头，8 KiB消息也至少需要6帧，100条至少600帧；精确分片、控制帧与A/B计数还要另算。如存在其他批次/采样口径，表中没有解释清楚。**不能把60抄成断言，也不能未经定义就把600当作本项目的最终计数。**
2. **表3-7，p.21 / PDF第27页：** 正文区分1518 B帧与1471 B载荷，表内又出现“最大消息负载1518B”等表述。用例落地前必须分清帧长、IP/UDP载荷与应用消息长度。
3. **§3.2.2–3.2.3，pp.18–19 / PDF第24–25页：** 8K是涉及分片/重组的上层消息能力，不能因此把当前项目的单帧 UDP 载荷上限改成8K，也不能不声明范围就加入完整分片重组功能。

**正确做法：** 冻结计数对象（单网/双网、消息/分片/帧、是否含控制报文）与长度单位，再由独立报文生成器/参考模型计算期望值，最后与 DUT 比较。

### 5.3 不能从本篇得到的结论

- **§3.2.5，p.20 / PDF第26页** 的 RTC 测试主要验证递增和同步更新，不等于证明绝对误差≤1 μs，也不能解决项目默认1 Hz PPS与4 ms失步超时的契约问题。
- **§5.3，pp.47–48 / PDF第53–54页** 比较的是人工与自动化测试的执行效率，并排除了可靠性测试。其“自动化100%”不能用作完整协议覆盖率、网络性能或本项目 PASS 证据。
- 本篇没有为 SNMP SET 的事务原子性提供专门 oracle。该类用例要按 RFC 和项目接口补充。

## 6. 对当前代码的建议：最小范围，不重做整机

本轮重新读取的 `snmp_lite.v` 与上轮审计版本一致：`in_ready` 仍固定为1，`P_RESOLVE2` 仍逐 VarBind 立即写入；顶层 SNMP `in_ready` 仍未连接到上游。本轮没有修改这些文件。

| 修复方向 | 建议触及的位置 | 必须保持/明确的条件 |
|---|---|---|
| 请求所有权与满载处理 | `snmp_lite.v`；必要时 `mgmt_sap_rx.v` 和顶层接线 | 活动请求及元数据不被覆盖；槽位容量固定且可验证；完整背压或整包拒绝计数必须二选一并贯彻 |
| SET 校验与提交分离 | `snmp_lite.v`、顶层实际写回/仲裁路径 | 所有拒绝条件在副作用前检查；整份写意图暂存；每笔写被真正接纳；按版本返回正确错误 |
| OID/GETNEXT 多周期处理 | `snmp_lite.v` 与 MIB/统计 RAM 查询接口 | 对象/后继索引、地址、数据、错误和请求标记一起过流水；不改变已冻结的 OID 行为 |
| 测试可信度 | SNMP TB、T13、回归判决与归档脚本 | 真实失败会阻止通过；输入/期望独立；日志按用例结构化绑定；不覆盖旧失败证据 |

推荐先评估**固定容量请求槽位＋包级接纳决定**。活动槽位和待处理槽位是可选的实现组织方式，论文不规定必须有两个槽位，也不提供无限负载下零丢包的保证。满时若不能保证完整内部背压，则必须明确整包拒绝与统计；不能只把 ready 拉低，而上游继续写。

原始以太网接收与内部背压不是一回事。内部拥塞不能让外部 GMII 任意暂停，入口无块/无容量时也要有明确的丢弃与恢复路径。

时序阶段可采用如下**工程候选结构**：

```text
请求快照/锁定
    → OID与VarBind上下文寄存
    → 对象或GETNEXT后继索引
    → MIB地址寄存与同步读
    → 数据/错误结果寄存
    → 校验汇总或事务提交
    → 响应缓冲
```

这不是三篇论文中的现成电路。优先拆上轮报告实际指出的 SNMP OID→RAM 地址热点，而非先重写全部 TX/RX 配置表。增加阶段后仍须完整回归，再在原8 ns条件下进行多角 post-fit；本轮没有新的时序测量。

## 7. 建议新增的验证项

以下均为**待实施、未执行的设计用例**，不是新增 PASS。完整条件见配套 `AFDX_文献落地验证清单_20260928.csv`；建议名尚未占用现有 T 编号。

请求守恒以明确的 SNMP 管理接入边界为统计域，与物理帧、IP分片和A/B冗余副本计数分开；也要约定未ACK响应是否仍属“在途”，避免重复或漏计。

| 建议用例 | 核心激励 | 关键判据 |
|---|---|---|
| SET_ATOMIC_1 | 前一个对象可写，后一个只读 | 整份请求报错，所有目标值保持原状；错误索引准确 |
| SET_ATOMIC_N | 第1/中间/最后变量非法，含最大 VarBind 数边界 | 不发生部分提交，不把后续合法项单独写入 |
| SET_PRECHECK | 响应太大、值域/类型/资源条件不满足 | 在产生写副作用前拒绝，按明确的版本/子集契约反馈 |
| REQ_BURST | 响应持续未 ACK，连续输入多个请求 | 每个完整到达报文有完成、明确拒绝或仍在系统内的归属，无静默消失 |
| REQ_CONTEXT | 不同源端口/源信息、请求 ID 和负载交错 | 数据、元数据和响应关联不串包 |
| QUEUE_BOUNDARY | 满/空、同拍入出、深度与深度+1 | 计数守恒；被拒绝报文不改写活动槽位 |
| RESET_RECOVERY | 接收、解析、预提交、提交/响应期间复位 | 符合冻结的复位状态；无迟到响应、悬挂槽位或幽灵写入 |
| GETNEXT_PIPE | 首尾、跨组、缺失项、输出背压、各阶段复位 | OID次序和值保持正确，控制标记与数据对齐 |
| SAP_SHARED | SNMP拥塞同时有TFTP/其他SAP与释放竞争 | 明确共享资源阻塞边界，无块泄漏或双重释放 |
| LATENCY_GATE | 合法流量下测时延，并人为增加被测延迟 | 正常满足已冻结阈值；越界必须 FAIL，不仅打印数字 |
| VERDICT_GATE | 失败后打印PASS、运行错误后PASS、缺终态/超时 | 框架不得报告PASS；预期负例与真正失败有不同标记 |
| POSTFIT_CHECK | 修复及流水版本完整回归后冻结并重新 Fit | 核查实际 setup/hold 与约束覆盖，不以工具 rc=0 代替时序合格 |

顺序建议：**先把失败用例和判决门做可靠 → 修 SET 和请求所有权 → 顶层与完整功能回归 → 再做时序优化及新的指标取证。**
