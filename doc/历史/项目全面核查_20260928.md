**项目有可信的完整功能回归基线，但还不能宣称功能、指标与比赛交付全部完成。** 本次核查确认：

1. 既有 **56/56 PASS** 不是简单的文档宣称：CSV、manifest、逐项 console 和归档哈希相符，所列 76 个冻结输入与当前工作区一致。

### A01｜SNMP 失败 SET 发生部分写入

**复现：** 一个 SNMPv1 SET PDU 含两个 VarBind：先给可写的 `afdxEsCtl` 写 `0x1234`，再给只读的 uptime 写值。最终响应错误为 4、error-index 为 2，但控制对象已经从 `0x051C` 变成 `0x1234`。

```text
AUDIT_SET_ATOMIC FAIL response_error=4 error_index=2
control_before=051c control_after=1234
```

**根因位置：** `rtl/mgmt/snmp_lite.v:522–541` 在每个 `P_RESOLVE2` 阶段立即产生 `ctl_we` / `vl_bag_we`，没有等待同一请求的所有 VarBind 完成校验。后续 VarBind 报错不能撤销前面的副作用。顶层的控制影子寄存器也在写使能时更新，见 `rtl/top/AFDX_top.v:1285`。

RFC 1157 §4.1.5 的 SET 流程是在前述错误条件均不适用时才赋值，并要求同一消息中的赋值表现为同时生效。当前行为不满足这一事务语义。[3](https://www.ietf.org/rfc/rfc1157.txt)

**建议：** 将“解析/权限/类型/范围校验”和“提交写入”分阶段；先保存整份写意图，全部通过后再提交。不能只在返回错误时改响应码，而保留已经发生的写入。

**关闭条件：** 有效多变量 SET 全部生效；任意位置存在未知 OID、只读对象、坏值或格式错误时，所有目标对象保持原值。至少覆盖 CTL 与 VL BAG 写回，并补顶层路径测试。

### A02｜SNMP 待决请求静默覆盖

**复现：** 请求 17 的响应保持未 ACK，继续送请求 18、19；请求输入始终 `ready=1`。实际响应序列为 17、19，18 消失，`drop_pdu_cnt=0`。

```text
AUDIT_BURST first_response_id=17 ready=1
AUDIT_BURST FAIL accepted_ids=17,18,19 response_ids=17,19,-1
parsed=2 responses=2 drops=0
```

**根因位置：**

- `rtl/mgmt/snmp_lite.v:103`：`in_ready` 固定为 1。
- `:366–380`：不论处理/响应状态，输入都能改写同一个 `req[]`、`have_pkt` 和元数据；待决只用一位标记。
- `rtl/top/AFDX_top.v:1293–1308`：SNMP 的 `in_ready` 未接回上游。
- `rtl/mgmt/mgmt_sap_rx.v` 的 STREAM 路径没有下游 ready 输入。

这是**内部接收契约与丢弃可观测性问题**；这里并不声称 UDP 网络绝对不得丢包。

**建议：** 明确选择完整的背压、请求队列，或“忙时整包拒绝并计数”策略，并保持正在处理请求的缓冲与 peer 信息稳定。**仅把 SNMP 的 ready 拉低不够，上游目前没有消费该信号。**

**关闭条件：** 长时间响应背压、连续多个请求和不同请求 ID/源端口下，无请求内容串扰；每个被接受请求有应答或明确、可核对的拒绝归因。再从真实 SAP 入口测试两种 IF_MODE，检查块归还守恒。

> A01/A02 的证据为 `snmp_probe.log`、`snmp_probe.json` 与 `probes/tb_snmp_audit.v`。正常串行 GET 对照通过，编译 0 errors。仿真器进程退出码为 0，但 **TB 行为判决是 FAIL**；本报告保留这一区别。两项尚未做顶层入口动态复现，不能虚称已经完成顶层失败取证或修复验证。

### A03｜T13 的上限参数未参与断言

`sim/tb/tb_t13_latency.v:175` 声明 `expected_max_total_ns`，去掉注释后该名字在全文只出现 **1 次**，即仅有声明。`:272–281` 只计算并打印时延；`:340–346` 虽传入三个上限，实际没有比较。

| IF_MODE=0 用例 | 传入但未使用的上限 | 归档实测 Total | 归档结果 |
|---|---:|---:|---|
| 最小帧 | 10 μs | 12.496 μs | PASS |
| 中等帧 | 50 μs | 50.424 μs | PASS |
| 最大帧 | 200 μs | 244.856 μs | PASS |

**这不直接证明违反指南的 1–2 ms 指标**：这些参数可能是旧口径，当前 Total 还包含 TB 抓帧后回灌。它确实证明了“该 PASS 没有验证传入的时延上限”。

**建议及关闭条件：** 先统一测量起止点、接口模式、负载、是否含回灌/交换机，再设定有依据的上限和真正的失败断言；加入人为增加延迟的负向测试，证明越界会 FAIL。不要简单启用旧数字后迁就失败放宽阈值，也不能把删除参数当作性能验收完成。

### A04｜回归器存在假绿路径

`sim/run_regress.ps1:232–245` 只保存最后一个含 `PASS|FAIL` 的行，再根据该行和进程 rc 判定。对相同 PowerShell 判决片段的最小输入测试得到：

| 合成输入，rc=0（除注明外） | 现有逻辑结果 | 应有处理 |
|---|---|---|
| 仅 PASS | PASS | 正常对照 |
| FAIL → PASS | **PASS** | 不应掩盖此前失败 |
| Runtime Error → PASS | **PASS** | 必须结合错误/断言状态判断 |
| PASS → FAIL | FAIL | 正常对照 |
| PASS，rc=1 | FAIL | 正常对照 |

`sim/run_one.tcl` 已有 `onerror`，能处理一部分 Tcl/仿真器错误；这不能补足所有“rc=0 且日志中已有失败”的判决漏洞。

**边界：** 本次独立扫描的既有 56 项日志未出现上述 FAIL/运行时错误迹象；不能因为发现判决器漏洞就倒推那一轮全部无效。

**建议及关闭条件：** 使用唯一、结构化的 case 终态，合并退出码、超时、编译/运行错误和断言计数；明确预期负例的标记方式。让上述探针及缺失结果、重复结果、未知测试 ID 等框架测试通过。证据见 `runner_verdict_probe.log` 和 `fresh_checks.json`。

|---|---:|

| 时钟约束 | 8.000 ns / 125 MHz |
| Slow 900mV 85°C setup WNS / TNS | **−1.735 ns / −1602.121 ns** |

`post_fit_setup.rpt:23–72` 列出的 **50 条最差路径全部**从 `g_snmp.u_snmp|oid_len[*]` 出发，终点都是 `vl_stat_mem` 的同一个 RAM 读地址寄存器。最差路径中互连约 6.172 ns，占数据物理延迟约 67%。相关 RTL 为 `snmp_lite.v:260–297, 513–519` 和 `AFDX_top.v:336–344`。

**建议：** 在修复 SNMP 功能契约后，优先拆分 OID/GETNEXT 解析、对象地址计算与 RAM 读控制的长组合路径，重新检查综合后真正的寄存边界；配置表 BRAM 化保留为资源/后续热点优化，不应仅凭旧交接推定它是本轮首要瓶颈。

**关闭条件：** 同器件、同 8 ns 约束的新冻结版本完成多角 post-fit，相关内部 setup/hold 不再违例；同时通过新旧功能回归。不要通过降频或无依据的 false/multicycle path 把报表做绿。

**范围说明：** 当前无真实板卡/IO 预算，check_timing 报告 72 个 no-input-delay、123 个 no-output-delay；这是内部时序自证的边界，不应伪造 IO delay。赛题无板仿真交付与 125 MHz 硬件实现声明分开评估，不能把板级签核强加为原任务的必交项。

## 4. 需求—实现—证据的剩余边界

以下主要是**范围与证据缺口**，不应一律写成已证明的 RTL bug。

| 方向 | 目前有依据的结论 | 仍需补充/确认 |
|---|---|---|
| MAC / 100 Mbps | 模式 0：125 MHz、10 拍/字节；模式 1：连续字节，接口能力约 1 Gbps | 问答只明确“GMII”；评测的字节时钟、帧内 valid/ready 语义与速率适配仍需明确。不可把连续 1 Gbps 结果当 100 Mbps 证据 |

| 128 TX / 4096 RX VL | 有表容量、前门写读、查表与边界测试 | 容量/索引覆盖不等于 128/4096 条 VL 同时持续收发 |

### 特别待确认：RTC 默认 PPS/失步契约

`rtl/top/AFDX_top.v:39–40` 默认 `RTC_US_PER_SEC=1,000,000`、`RTC_SYNC_TO_US=4,000`，`:1364` 又把 `sync_vld` 接为 0。`rtc_sync.v:116–122` 在连续约 4,000 个 μs tick 无 PPS/同步事件后置失步。

**若默认部署是仅 1 Hz PPS，这个 watchdog 会远早于下一次正常 PPS 到来。** 当前 T16 用了缩短秒周期的参数，不能覆盖这项默认组合。应确认是需要独立的 PPS watchdog、放宽 PPS 模式超时，还是必须接入周期同步报文。

这是**代码层面的高风险待核验项**；本轮没有运行默认 1 秒时基的专项实验，不把它计入“已动态复现的两个 SNMP 缺陷”。
