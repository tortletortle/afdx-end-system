## 三、已复现的根目录问题

### F-01｜RM 的 8 位历史窗不等于顺序交付保证

**当前源码位置：** `rtl/rx/rx_rm.v:98–142`；关键逻辑是 `behind` 只覆盖落后 1…8，且未在历史位图中出现的旧 SN 会被 forward 并补位。

**独立规范核对：** `AFDX_补充文献/ARINC664P7_spec.pdf`，145 页，2005 版，印刷页 26 / PDF 第 34 页。原页明确写道：

> “The Redundancy Management function must forward only in-sequence frames, but reordering is not required.”

同页 A2 丢失、A3 先到、B2 后到的例子明确规定 B2 不交付。IC 与 RM 是分开的保证，不能用“B 网 IC 接受了 B2”证明它可在 A3 后交付。

**本轮测试：** `probes/tb_review_ic_rm.v`，连接真实 `rx_ic` 输出到真实 `rx_rm`，只传递 IC 接受描述符；NUM_RX_VL=2，VL0，双网，SkewMax=16,384 μs。

#### 反例 A：补洞导致乱序

| 输入 | 时间戳 μs | 期望 forward | 实际 |
|---|---:|---:|---:|
| A / SN1 | 1000 | 1 | 1 |
| B / SN1 | 1100 | 0 | 0 |
| A / SN3 | 3000 | 1 | 1 |
| B / SN2 | 3100 | 0 | **1** |

实际转发顺序为 **1、3、2**。

#### 反例 B：历史窗外副本再次转发

A 网依次 SN1…10，时间戳 1000…10000 μs；B 网 SN1 于 11000 μs 到达，相对 A1 延迟 10000 μs，小于 SkewMax，但实际仍 forward。

#### 正向/邻域对照

- 落后恰好 8 个序号：正确删除。
- 同 SN 真正超出 SkewMax：接受并产生 skew 事件。
- 254→255→1→2 回绕及该序列内旧副本：所测场景正确。
- 每次输出施加 8 拍背压：输出保持检查未失败。

**结果：32 次 IC 事务均被接受；32 次 RM 判决检查中 2 次违反期望。** 仿真 rc=1，由明确断言终止。

**范围限制：** 此项是 IC→RM 组合证据，不是整机 MAC→应用端口的动态复现。本轮不能宣称已检验所有复位、长时间戳回绕与满配并发。

**修复建议：** 先依据序号环、严格超时、复位假设确定状态机，再实现顺序接收契约；不能只扩大位图或继续“未见旧 SN 补洞”。增加真实顶层交付顺序/次数/块回收测试。

### F-02｜调度器长期空闲导致半周期歧义

**源码：** `rtl/tx/tx_vl_scheduler.v:90–91`：

```verilog
age = tb_us - nt_q;
due = val_q & ~inflight[idx_d] & port_ready[port_q] & ~age[23];
```

`next_tx` 只在配置或发送反馈时更新。启用 VL 长时间无消息时，目标时间不会自动推进；24 位差值的最高位在半周期后变为 1。

**本轮构造：** 默认 128 TX VL，仅 VL0 有效，BAG=1000 μs；配置时 tb_us=0，端口无消息、无在途帧、builder 空闲。随后设置时间并提交就绪，在 1024 拍窗口观测首次 `sch_take`。

| 新消息出现的 tb_us | 首次 sch_take | 判定 |
|---:|---:|---|
| 1,000,000 | 第 252 拍 | 正常对照 |
| 8,388,607 | 第 252 拍 | 半周期前正常 |
| 8,388,608 | 未出现 | **失败** |
| 9,000,000 | 未出现 | **失败** |
| 0（完整回绕等价状态） | 第 252 拍 | 恢复对照 |

半周期为 **8.388608 秒**，完整周期为 **16.777216 秒**。

**边界说明：** 使用模块外部时间输入跳跃加速，没有实跑 9 秒物理时间。对于本版本，“无消息、无反馈、无重新配置”期间不会修改 next_tx，足以构造该状态；如果修复后新增老化状态，必须重新设计测试，不能沿用跳过其更新过程的办法。本测试也没有检验后续 ACK/发帧/BAG 全档。

**修复建议：** 建立明确的到期/老化表示与发送反馈规则；不要简单删除最高位判定导致提前发帧，也不要仅加宽计数器便宣称无限空闲正确。

### F-03｜截断 SNMP SET 仍产生写入

**根因线索：** `snmp_lite.v` 虽记录 `req_len`，但当前解析流程没有据此完成接收长度与逐层 TLV 边界约束；访问 `req[pp[7:0]]` 会读取上一个请求留下的内容。

#### 独立单元测试

先用合法 SET 将 CTL 设为 `0x1234`；再发送设置 `0x5678` 的请求，但删除最后一个字节。

```text
sent_bytes=45
received_response=1 response_error=0
control_before=1234 control_after=5634 writes=1
```

接收缓冲中残留的 `0x34` 被拼入新值，形成 `0x5634`。这是**真实写入副作用**，不是单纯错误码不准确。

#### 顶层复现

使用现有候选目录的 T15c 激励/BER 解码基础，提取不依赖候选新接口的 BAG 与截断包场景，保持原断言。报文通过真实 MAC 接收、PMEM、管理 SAP 到 SNMP；网络帧自身格式/校验有效，截断的是内部 BER 内容。

两档均得到：

```text
received_payload_bytes=44
control_before=1234 control_after=5634
response_error=0 write_delta=1 snmp_drops=0
```

单元与顶层的 BER 编码不同，所以分别为 45 / 44 字节，不混写为同一个输入。

**候选副本对照：** 相同定向测试下，单元不写入；两档顶层通过。这里只证明被测反例及对照，不证明所有 ASN.1/BER 边界。

**修复建议：** 接收实际长度、外层与各层容器终点、整数长度/类型、请求与响应容量一起校验；错误发生在提交前。维持 A01 原有“先校验后提交”，但不能以其通过代替语法边界正确性。
