## 2. P1：正确性

### OPT-1 RM 迟到副本重复交付 → SN 滑动接收窗口

**现状（已读代码确认）**
- `rx_rm.v:7-11,87-111`：每 VL 一个 33 bit 表项 `{seen, last_ts[23:0], last_sn[7:0]}`。唯一丢弃条件是 `seen && sn==last_sn && |ts-last_ts|<=Skew`，其余一律转发。
- `tb_t10_top_rm.v:282-285` 原文：*“RM keeps only the LAST forwarded SN (7.11), so a late copy older than last_sn … is forwarded again; the model predicts the same (documented limitation).”* TB 的参考模型也按这种行为预测，所以 T10 是 PASS，**但行为本身会重复交付**。
- 触发条件：一侧网络落后超过 1 个 BAG（交换机排队、链路抖动），落后一侧的副本会全部再交付一次。这直接对应 REQ-REL-02 的缺口。

**文献**
- L105 Täubrich：分析了 RM 算法在“顺序、丢失、重复”三者之间的取舍，并证明只记 last SN 的实现会重复交付。
- L107/L108 Meng Li：给出了 SN 回绕和窗口宽度的约束。
- L137 RFC 4303 §3.4.3：“最高 SN＋W 位位图”的滑动窗口，是精确判重的成熟结构。

**改法（在原表项上加宽 8 bit：33→41 bit）**

```text
RM_ST[vl] = {seen, last_ts[23:0], last_sn[7:0], hist[7:0]}   // hist[k]=1 表示 last_sn-(k+1) 已交付
d = ring255(sn - last_sn)        // SN 取值 1..255，0 表示发送端复位；ring255 取 0..254
if (!active || !seen || sn==0)            -> forward，resync（last_sn=sn, hist=0）
elif (d == 0)                             -> 原规则不变：|dts|<=Skew 丢；否则转发并记 skew 事件
elif (1 <= d <= 127)   /* 更新的帧 */     -> forward；hist = (hist<<d) | (1<<(d-1))；last_sn=sn；last_ts=ts
elif (back = 255-d; back <= 8)            -> 已在窗口内：hist[back-1]? 丢(rm_late_dup++) : forward 并置位 hist[back-1]
else  /* 落后超过 8 个 SN */              -> 策略位 RM_OLD_POL：0=转发（保交付），1=丢弃（保不重复），并记 rm_old_evt
```

- **不丢帧、不重复**：落后不超过 8 个 SN 时精确成立。超过 8 个时，由策略位显式选择，不再“静默重复”。
- 位图不能出现歧义的条件（写进配置工具 `bag_budget.py` 做检查）：`SkewMax_VL < 127 × BAG_VL`。现有 `skewmax_exp` 最大可配到 4<<15 μs ≈ 131 ms，当 BAG=1 ms 时这个条件会被违反。所以**配置工具应拒绝 `SkewMax ≥ 127·BAG` 的组合**。这一条同时也是给文档补充的约束。
- 时序：`ST_CMP` 多一个 8 bit 模减、一个 8 选 1 和一个移位器，都在 1 拍以内。状态机仍是 4 态，吞吐不变。
- 存储：4096×41 bit，与原 4096×33 相比，BRAM 块数视器件的宽度配置而定，多半不变（M9K 的 ×36/×18 拼接需要重新核算）。

**验收**
1. 把 `tb_t10_top_rm.v:282-285` 这段“documented limitation”改成**硬断言**：A 追上时的 24/25/26 必须 drop。
2. 新增场景：B 落后 1/3/8/9 个 BAG；SN 从 255 回绕到 1；SN=0 复位；两网交替领先；babbling（同 SN 反复出现）。
3. 参考模型用“已交付 SN 集合”的精确语义实现，不要与 RTL 同构。
4. 56 项全量回归，重点看 T10/T10g/T08b。

### OPT-2 SNMP SET 两阶段提交（A01）

**现状**：`snmp_lite.v:532-537` 的 `P_RESOLVE2` 每解析出一个 varbind，就立刻拉高 `vl_bag_we`/`ctl_we`。如果第 k 个 varbind 出错，前 k−1 个已经生效，违反 RFC 3416 §4.2.5 的“as if simultaneously / 全部或全不”（L116）。

**改法**
```text
P_RESOLVE2：只做校验，把 {目标, 值} 写入已有的 vb_* 暂存数组，不产生任何 *_we
         → 全部 varbind 过一遍后
P_COMMIT ：if (err_st==0) 按 vb_idx 0..nvb-1 逐拍产生 *_we；else 什么也不写，直接组织错误响应
```
- 两阶段的第二阶段只是按序回放暂存值，不可能再出错，所以不需要 undo。这也是 RFC 3416 推荐的做法。
- 要求 `nvb ≤ vb_*` 的深度。超出时在第一阶段直接返回 `tooBig`/`genErr`。

**验收**：新增 T13x 场景：“第 2 个 varbind 类型错”→ 第 1 个目标寄存器前后读值不变，响应 `error-index=2`。可以再加一个变异体：把 `P_COMMIT` 的 `err_st` 判断删掉，确认 TB 会判 FAIL。

### OPT-3 SNMP 请求覆盖（A02）→ 忙时丢弃并计数

**现状**：`snmp_lite.v:367-375` 只要 `in_vld=1` 就写 `req[]`。正在处理一个请求时，如果又来一个包，当前请求的缓冲会被破坏。

**改法**（推荐 a，最省）
- a) `accept = in_vld && !have_pkt`；忙时整包丢弃，`snmp_busy_drop++`，并通过 MIB/统计窗口暴露这个计数。理由是 UDP/SNMP 本来就允许丢包，由管理站超时重发；而且 §8.7 规定 RX 不反压，两者口径一致。
- b) 需要背靠背处理时，用双缓冲（ping-pong）：代价是多一份 `req[]` 存储。

**验收**：TB 在响应完成之前注入第二个请求 → 第一个响应的字节逐一比对正确，`busy_drop` 加 1。

### OPT-4 回归判决结构化（A04）＋ T13 断言（A03）

- **A04**：`run_regress.ps1` 不再只 grep 日志关键字。每个 TB 结束时输出一行机读结果，例如 `VERDICT T10 PASS checks=312 errors=0`。runner 满足以下全部条件才算 PASS：**有且仅有一行 VERDICT**、`errors==0`、`checks>0`、退出码为 0。没有 VERDICT 一律按 FAIL。这样可以堵住“什么都没跑也是绿”的假绿。
- **A03**：T13 加入端到端时延断言。RX 侧阈值取 XAPP1130（L001）给出的 <150 μs 量级，并在文档中标明“参考公开 AppNote 量级，非 Part 7 条款”。
- 配套做法（L117）：给 OPT-1/2/3 各准备 1 个变异体，放进现有的 `test_t12_mutants.py` 机制，证明新断言确实“咬得住”。

## 3. P2：时序、架构一致性、存储

### OPT-5 SNMP OID 解析流水化（A05：WNS −1.735 ns，最差 50 条路径都在这里）

**现状**：进入 `P_RESOLVE`（`snmp_lite.v:513`）的那一拍，`o_g/o_l/o_i`、`pfx_ok`、`walk()`、`idx_of` 全部由 `oid_len/oidb` 组合求出（`:261-289`），再打入 `rq_*` 驱动 `mib_*` 的 RAM 地址。这是一条“可变长 OID 比较 → 索引运算 → RAM 地址”的长链。

**改法（L115 retiming 思路，但手工切分更可控）**
1. **边解析边算**：OID 子标识符是逐字节到达的，`pfx_ok` 可以按字节增量比较（每来一个字节与常量前缀比 1 字节，结果累积成 1 bit），`o_g/o_l/o_i` 在对应位置到达时直接锁存。进入 `P_RESOLVE` 时它们已经是寄存器，组合深度降到“寄存器 → 选择 → 地址”。
2. `walk()`（GETNEXT 的后继计算）单独占 1 个状态 `P_WALK`，结果寄存后再发 `mib_*` 地址。
3. 每个请求多 1~2 拍（8~16 ns），相对 SNMP 的 ms 级交互可以忽略。

**验收**：同一器件、同一约束下重跑 post-fit，看 `snmp_lite` 路径是否退出 Top-50，以及 WNS 的变化。SNMP 相关 TB（T13 系列）逐字节比对不变。

### OPT-6 D10 发送错相：文档与 RTL 不一致，需要收口

**核实结果**
- 0924 两份文档写的是“`tx_vl_scheduler` **内置**正交错相偏置 Δt=26 μs（26i=16i+8i+2i 移位加）”。
- 实际 RTL：`tx_vl_scheduler.v:18` 仍是“`cfg_we` 写入时 `next_tx <= tb_us`（立即到期）”，全文没有 offset/phase 逻辑；`AFDX_top.v:1119-1121` 也只传入 `bag_us/port`。
- 实际做法：T05b 的 TB 在 `:162` 注释写明 *“Stagger the actual MSG_WR”*，也就是由**主机按相位错开提交消息**。跟踪表写的是“按 VL/BAG 进行错相**提交**”，与 RTL 一致。
- 调度器语义：首帧时刻由消息到达决定，之后 `next_tx = 帧起始 + BAG + 1`。所以只要主机错开首次提交，相位就会一直保持。一旦主机同时提交，801 μs 的同相排队仍会复现。

**二选一**
- **方案 A（零 RTL，推荐比赛阶段采用）**：把 D10 明确定义为**主机契约**。
  - `bag_budget.py` 输出每条 VL 的建议首发偏移 θᵢ。可以用 L099–L101 的 offset 分配启发式，最简单的是 θᵢ = i·BAG/N。
  - 驱动或示例程序按 θᵢ 提交。
  - 利用已有的 `w7.max_jit_us / bag_ovf` 统计，在运行时自检契约是否被违反。
  - 同时修正 0924 文档对 D10“内置偏置”的描述。
- **方案 B（硬件保证）**：每 VL 增加一个 `phase_us` 字段（可放在 Q20 表 `0x0480+vl` 的 [31:21] 空位，以 16 μs 为单位，11 bit 最大约 32 ms），并加一个 VL 级 `phase_lock` 模式位。
  - 当 VL 空闲超过 1 个 BAG 后重新到达时，令 `next_tx = 下一个满足 (t − phase) mod BAG == 0 的时刻`。BAG 是 2 的幂毫秒，取模可以化成截位。
  - 代价：首帧额外等待 < BAG。这对 ARINC 的“帧间隔 ≥ BAG”无影响，但会增加端到端时延，需要在报告中写清楚。
  - 纯 “26×i 开流偏置” **不够**：它只在开流瞬间消息已经就绪时有效，所以不建议照 0924 文档去实现。

### OPT-7 公共池借用：一致性与配额

**核实结果**
- 设计书 §8（第 490、972 行）写的是“公共池 4 块，**任一池**耗尽时借用”。
- `tx_port_buf.v:19` 实际是“TX 只用 `TX_POOL` 0..5，借用**留第 4 周与 `rx_port_buf` 统一仲裁**”，也就是 TX 不借用。
- `rx_block_pool`：分配时取 6..15 中最低的空闲号（专用池优先，然后公共池），**没有借用上限**。一次 RX 突发可以把 4 个公共块全部占满。

**改法**
- 最小改动：文档改为“公共池当前仅供 RX 借用”，与 RTL 对齐（零 RTL）。
- 进一步：给 RX 加借用上限 `borrow_cap`（寄存器可配，默认 4，即与现行为一致）。如果将来 TX 也要借用，按 L121 的 Dynamic Threshold 思想，令各池的阈值为 `T = α·(剩余公共块)`，α 取 2 的幂（例如 1/2），用一个比较器实现，避免一方独占。
- 配套分析：存储报告中提出的“RX 块池容量上界”（判决链恒定 20 拍，在途帧数上限；参考 L122）应该作为 `borrow_cap` 默认值的依据。

**验收**：T08b 块守恒判据不变；新增“公共池被 RX 占满后 TX 或另一方的行为”场景（如果实现了 TX 借用）。

## 4. P3：功能缺口、签核、验证

### OPT-8 RTC：比例环 → PI 伺服＋分数累加器（兑现设计书 F5“分数微调”）

**现状**：`rtc_sync.v:79` 为 `adj = big_jump ? err : (err >>> log2_avg)`，这是纯比例（P）环，没有频率项。

**问题定量**：本地晶振有频偏 f 时，每秒（每个 PPS）漂移 f μs（f 以 ppm 计）。P 环的稳态误差 = 每次更新的漂移 ÷ 增益 = f·2^log2_avg μs。例如 f=50 ppm、`log2_avg=2` 时约为 **200 μs**，而且越想平滑（log2_avg 越大）误差越大。现有 `locked` 的判据是“连续 LOCK_N 次 |err|≤1”，有频偏时可能永远达不到。

**改法（L133 RFC 5905 的 PLL 结构、L134 的 PI 伺服）**
```text
每个 PPS/同步事件（小误差分支）：
  freq_q  <= sat(freq_q + (err >>> KI_SH))      // 积分项：频率估计，Q.16 μs/s
  offset  <= offset - (err >>> KP_SH)           // 比例项：相位修正（与现在相同）
每个 tick_us：
  {carry, frac_acc} <= frac_acc + freq_q/US_PER_SEC 的定点近似  // 分数累加，溢出时 offset ±1
大误差分支（|err| > TH_JUMP）：直接 step，并且不更新 freq_q（与 RFC 5905 的 step 逻辑一致）
SYNC_LOSS：冻结 freq_q，继续按频率估计自由运行（holdover），比现在的“纯自由运行”更好
```
- 资源：一个 32 bit 累加器、一个饱和加法器，约 80 LUT。放在 `tick_us` 节拍上，不在关键路径上。
- **验收**：T16 增加“本地频偏 ±50/±100 ppm”场景（TB 让 PPS 周期偏离 US_PER_SEC）→ N 个 PPS 后 |err|≤1 μs，并且 `locked=1`；SYNC_LOSS 后 1 s 内的漂移显著小于 f μs。

### OPT-9 `pps_in` 的 CDC 签核（L132）

## 5. 明确不建议现在做的

- **OPT-11 调度器改时间轮（L135）**：现在 128 VL 顺序扫描一轮 1.02 μs，与最小 BAG 1 ms 差 3 个数量级。T05b 的稳态抖动判据是 50 μs 并且已通过。按 Varghese-Lauck 的分析，时间轮的收益在定时器数 n 很大时才显著。建议只在文档中给出扩容路径：VL ≥ 1024 时用按 μs 槽散列的单层时间轮。
- **OPT-12 配置 FF 阵列 BRAM 化（L125–L127）**：`tx_cfg_mem` 在顶层有多处组合读口（例如 `AFDX_top.v:1120-1121` 直接用 `tx_cfg_mem[...]` 连到调度器配置口），迁移到 BRAM 需要逐个读口分析延迟。应在拿到 Continue12 的 post-fit 资源和时序报告、确认它确实是瓶颈之后再做。
