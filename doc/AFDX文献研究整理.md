## 2. 新增主题结论

> 以下是 `[LIT]` 研究结论；其是否转化为本项目的设计决策和验证结果，请查 [AFDX项目应用追踪](AFDX项目应用追踪.md)。

### 2.1 共享内存与交换结构

`基于共享内存的 AFDX 航空网络交换机设计`等资料的题名将共享内存作为交换结构核心线索。对当前工程可吸收的不是具体端口数或存储器型号，而是以下设计问题：

- 多入口写入共享存储时必须定义仲裁、写入完成和 descriptor 提交顺序；
- 数据存储与控制信息可以分离，但块/descriptor 的所有权必须唯一；
- 交换机或端系统的共享内存架构应同时给出拥塞、溢出和回收策略。

这与当前 `rx_block_pool.v`、`rx_pmem_queue.v` 和主机/RX 写口仲裁直接相关，但仍需以当前 RTL 的长期块守恒测试为证据。

### 2.2 时间窗、轮询和时延上界

`基于时间窗的 AFDX 端系统调度策略设计实现`、`保证轮询时延上界的 AFDX 网络 VL 最优设计`和交换机调度相关资料把调度问题从“能否发送”扩展到“等待上界是否可证明”。对当前工程的启示是：

- 调度器需要记录 VL 到期时间、选择时间和实际 `frame_start`；
- 需要分别分析扫描延迟、队列等待、帧线上时间和 A/B 复制等待；
- 满载测试应报告最大等待、启动瞬态、稳态间隔和失败样本，不能只报告平均吞吐；
- 同相启动和起始相位错开应成为独立测试变量。

### 2.3 驱动、PCIe 与主机接口

Linux/CentOS 驱动、PCIe 端系统和应用程序方向的资料表明，AFDX 端系统交付不止是帧处理 RTL，还包括：

- 配置表加载和提交；
- descriptor 与 payload 的主机可见性；
- DMA/批量搬运或等效前门访问；
- 中断、队列状态和错误统计；
- 驱动复位、重试和资源回收。

这些资料只支持职责分层，不直接规定当前项目必须使用 PCIe、Linux、特定 DMA IP 或处理器。当前工程仍需完成 RX 端口到主机读回的闭环。

### 2.4 TAP、状态监控、时延测试与故障注入

TAP 卡、状态监控、端系统技术时延测试和故障注入相关资料补充了验证视角：

- 观测应覆盖原始帧、错误类型、VL、SN、A/B 到达关系和时间戳；
- 端到端时延要明确起止点、时钟、帧长、BAG、样本量和统计口径；
- 故障注入应验证坏帧不污染 IC/RM 状态、duplicate 不重复投递、资源耗尽后能够恢复；
- 旁路/并联采集适合观察网络，而不应被误当成端系统内部功能已实现的证据。

## 3. 可复核协议基线：L001

`xapp1130.pdf`（Architecting ARINC 664, Part 7 (AFDX) Solutions，Xilinx，2009）是本批最完整且可直接提取的参考资料。可复核要点包括：

- VL 组织静态流量、寻址和带宽约束；
- BAG 采用 1–128 ms 的 2 的幂档位；
- 发送侧按 BAG 调度、加序列号并通过 A/B 冗余发送；
- 接收侧按 VL 进行完整性检查、FIFO 缓存和冗余去重；
- FPGA 可承担 VL 收发、带宽控制、完整性和冗余管理，处理器承担更高层协议。

这些内容可作为架构参考，但不改变当前设计书的接口、SN 判决式、SkewMAX 参数、时钟或器件约束。尤其不能把 Xilinx 文档中的 FPGA/IP 组织直接等同于当前工程的综合结果。

## 5. 文献共同指向的 AFDX 结构

多篇文献虽然实现平台不同，但对端系统的基本数据流描述相近：

```text
双网 MAC/PHY
    ↓
帧解析、CRC/IP/UDP/长度等完整性检查
    ↓
VLID/配置表查找与过滤
    ↓
IC：每 VL 的 SN 完整性检查
    ↓
RM：A/B 副本去重和冗余选择
    ↓
IP/UDP 与通信端口解析
    ↓
采样端口或队列端口
    ↓
主机/应用读回
```

发送方向通常为：

```text
主机/应用消息
    ↓
发送端口缓冲
    ↓
VL 调度与 BAG 整形
    ↓
UDP/IP/AFDX 封装、SN 添加、FCS
    ↓
发送冗余管理
    ↓
MAC A/B
```

这套分层与当前工程的总体方向一致，但不能把文献中的“系统结构图”当作当前 RTL 已经闭环的证明。

## 6. 关键概念整理

### 3.1 VL、BAG、Lmax 与 Jitter

- VL 是通过静态配置定义的数据流/路径抽象，多条 VL 可以共享物理链路。
- BAG 规定同一 VL 相邻帧的最小发送间隔，文献中常见 `1、2、4、8、16、32、64、128 ms` 等 2 的幂档位。
- Lmax 约束 VL 允许的最大帧长度，BAG 与 Lmax 共同决定带宽和竞争影响。
- Jitter 不是单帧线上传输时间，而是帧相对于其配置发送节拍的偏差；必须区分启动瞬态、稳态、同相启动和相位错开。
- 文献给出了约 500 μs 级别的 jitter 上限讨论，但本项目具体判据仍以总体设计书和赛方约束为准。

**工程含义：**调度器需要以实际线上 `frame_start` 或等效发送锚点维持 BAG，测试需要输出每条 VL 的最小/最大间隔、启动和稳态 jitter，不能用单帧延迟或 Python 预算代替系统测量。

### 3.2 SN、IC 与 RM

- SN 为每条 VL 的帧序列标识，接收端需要维护每 VL 的状态。
- IC 负责判断连续、丢失、重复和乱序，并决定是否更新 PSN 状态。
- RM 负责双冗余 A/B 副本去重：同一 VL、同一 SN 的副本只允许一个进入后级。
- A/B 同拍、先后到达、链路单边失效和偏斜超时都需要确定性行为。
- 只有经过前级完整性判决的帧才能影响 IC/RM 状态；错误帧不能污染状态机。

**工程含义：**IC 和 RM 是两个不同的状态边界，不能将“SN 正确”直接等同于“应用消息已投递”。

### 3.3 采样端口与队列端口

- 采样端口保留某个 VL 的最新数据，新数据通常覆盖旧数据，需要 freshness/age 观测。
- 队列端口按到达顺序保留多条消息，需要深度、满、空、溢出和最终释放策略。
- 两类端口的数据所有权和块释放时机不同，不能仅用一个通用 FIFO 加配置位替代完整语义。

### 3.4 UDP/通信端口映射

文献把 VL、UDP 端口和端系统通信端口关联起来。接收端不仅要验证以太网/IP/UDP 字段，还要根据配置决定目标通信端口、端口类型和管理 SAP 分流。

### 3.5 Store-and-forward 与可观测性

为完成 CRC、长度、VLID、常数字段、BAG/Jitter 等检查，文献中的交换机/端系统通常先完整接收并形成 descriptor，再作后续判决。该方向与当前 PMEM 写入、帧完成后提交 descriptor 的设计一致。

## 7. 逐篇研究结论

### 4.1 《AFDX交换机的ASIC设计和实现》

文献重点是面向 ARINC 664 Part 7 的交换机 ASIC，强调 VL 支持、固定路由、错误过滤、全局统计和基于 BAG/Jitter 的警管。文中描述了 CRC、帧长、字节对齐、常数域、VLID 等错误的过滤统计，并对 ASIC 可测试性和 FPGA/实物测试进行了说明。

**对本项目的启示：**

1. RX 入口应采用完整帧判决后再提交 descriptor 的路径；
2. 错误分类和统计应成为可读的状态面，而不是只产生一个总 drop；
3. BAG/Jitter 应作为独立 policing/观测项；
4. 综合和仿真之外，还要保留可测试性、故障注入和统计读回设计。

**边界：**文献的 24 端口交换机、ASIC 工艺、功耗和实测结果不适用于当前单端系统 FPGA 规格。

### 4.2 《AFDX应用程序设计与实现》

文献从应用程序和实验系统角度说明 VLID、BAGValue、NetSel、SN、帧长度和静态路由表的配置关系，并通过板卡和交换机实验观察通信结果、帧数和字节数。

**对本项目的启示：**

- 配置表不是孤立寄存器，它必须能解释为 VL、网络选择、带宽和端口映射的组合；
- 端到端测试至少要同时核对帧数量、字节数量、VL/端口选择和接收内容；
- 主机配置加载与运行时数据路径应有明确边界。

### 4.3 《AFDX网络数据分析系统设计》

文献提出通过测试设备旁路或串联采集双冗余网络流量，由主机软件实时统计数据流量、错误和典型帧长度，并用多交换机、多个端系统的拓扑验证测试能力。

**对本项目的启示：**

- 测试接口应暴露帧数、字节数、错误类型和链路状态；
- 64 B、512 B 等典型帧长应进入回归样本；
- 仿真 scoreboard 之外，指标 CSV 和可复核的时间戳是后续性能验收的重要证据。

### 4.4 《AFDX网络端系统芯片设计与实现》

文献描述了集成处理器、AFDX 协议处理单元、双余度 10/100M MAC 和主机接口的 SoC 架构，测试项目覆盖基本功能、端口、地址管理、协议栈、冗余、配置表、RTC、BAG、发送/接收流量和系统应用。

**对本项目的启示：**

- 应把协议处理、端口/配置、冗余、管理和主机接口作为可分别验收的层次；
- 测试矩阵应覆盖配置表、RTC、BAG、流量和冗余，而不是只有帧格式；
- 文献所说的“完整测试”不能替代本项目当前版本的 RTL 证据。

### 4.5 《AFDX网络系统监控设计与实现》

文献重点是并联采集、统一授时、帧监控、VL 特性监控、链路状态监控和传输时标监控。其观测对象包括 BAG、Jitter、完整性参数、链路速率和交换延迟。

**对本项目的启示：**

建议逐步增加以下观测量：

- `t_rx_start`、`t_rx_commit`、`t_lookup_done`、`t_flt_done`、`t_ic_done`、`t_rm_selected`、`t_port_visible`、`t_host_read`；
- 每 VL 帧数、字节数、SN 异常、A/B duplicate、skew、BAG 违规和 jitter 峰值；
- 端口队列深度、PMEM 等待和块池耗尽/恢复。

这些是测量接口建议，不是当前规格新增寄存器。

### 4.6 《AFDX网络终端系统设计研究》

这是对当前 RX 后半链路最直接的参考。文献明确描述接收帧经过完整性检查和 VL 数据库比对，再进入 RM 去除重复副本，最后按 UDP/通信端口进入采样端口或队列端口。

**对本项目的启示：**

- `rx_ic`、`rx_rm`、`rx_ip_udp_parse`、`rx_port_buf` 应保持清晰的模块边界；
- RM 只允许一个冗余副本进入后级；
- 采样端口必须支持覆盖，队列端口必须支持顺序积压；
- 端口读回完成前，PMEM 块不能提前归还。

### 4.7 《基于FPGA的AFDX协议处理芯片设计》

文献把 FPGA 作为 VL 调度、流量整形、完整性检查和冗余管理的硬件载体，并强调 BAG/Lmax、SN 和双路径可靠性。其软件部分负责初始化、配置、存储管理、中断和高层协议协调。

**对本项目的启示：**

- 当前 TX 调度、MAC、SN、IC 和 PMEM 化路径与这种软硬件边界相容；
- 需要继续明确初始化扫描、配置提交和运行态状态 RAM 的所有权；
- 软件/主机管理面不能被局部帧级仿真替代。

### 4.8 《基于FPGA的AFDX软硬件协同设计》

文献采用 SoPC/PCIe 方向，强调 PLB/PCIe slave 寄存器访问、master/DMA 数据搬运、descriptor、双网 AFDX IP 和软件实现 SNMP/ARINC 615A 等高层功能。

**对本项目的启示：**

- 主机前门、descriptor、PMEM 和批量读回应形成稳定契约；
- 低层确定性数据路径适合硬件，管理协议和配置服务适合软件/主机侧；
- 当前 `host_if.v` 占位、RX 主机读回、统计/中断和管理面仍需分别收口。

**边界：**Virtex-5、PowerPC、EDK、PLB、PCIe 和 vxWorks 是文献实现环境，不是当前工程的器件或平台要求。

## 10. 优先级建议

### P0：完成 RX 纵向闭环

1. 统一 `rx_ic` 为 PSN RAM 的唯一所有者，移除顶层重复 PSN 语义；
2. 明确 descriptor 和 PMEM block 的唯一所有权转移；
3. 实现 `rx_rm`：同拍、先到、偏斜、duplicate、超时和 backpressure；
4. 实现 IP/UDP 到通信端口的解析和映射；
5. 分开实现采样端口覆盖与队列端口积压；
6. 完成主机读回、释放和最小单 VL 双网回环。

### P1：补齐确定性、可观测性和长期稳定性

1. 完成合法 BAG 全档和同相/错相满载测试；
2. 分别记录启动瞬态和稳态 jitter；
3. 增加端到端时间戳和每 VL/每端口统计；
4. 覆盖持续主机/RX 仲裁、端口满、块池耗尽/恢复和长时间随机流量；
5. 在目标平台上分别取得综合、资源和 125 MHz STA 证据。

### P2：管理面和交付收口

- 统计寄存器、真实事件中断、RTC、SNMP、ARINC 615A/TFTP；
- 文献条款与总体设计书的冲突登记；
- 完整测试矩阵、指标 CSV、波形说明和可复现归档。
