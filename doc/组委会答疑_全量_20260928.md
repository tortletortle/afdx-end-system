## 1. 选题一：仿真与评测方式（**最关键**）

| 问 | 答（原话） |
|---|---|
| AFDX 仿真结果验收是自己写回环，还是要和赛方仿真模型/其余验证模块通信？ | **需要参赛者自己编写仿真激励（文件）并验证内容。** |
| 是否有仿真文件和参考测试环境？ | 需要参赛者自己编写仿真激励（文件）并验证内容。 |
| 仿真是否必须基于 FPGA 做波形仿真，还是允许搭建其他软件运行环境完成功能测试？ | **要求基于 FPGA 做仿真。** |
| 最终评测会运行参赛者自己的 testbench，还是使用其他测试？ | **评测会用到参赛者的 Testbench。** |
| 要求 RTL 仿真、综合后仿真还是布局布线后仿真？ | **综合后仿真即可。** |
| ARINC 664 P7、SNMP、615A、RTC 分别按什么版本及必测功能验收？是否提供测试子集或参考激励？ | **不对协议版本做规定，也不提供参考激励。** |

### 对本项目的影响（需要决策）

1. **`综合后仿真即可` 是本轮最重要的一条。**
   当前 56/56 全部是 **RTL 行为级仿真**，仓库里没有综合后（门级 + SDF）回归。
   「即可」可以读成"门级仿真就够了、不必做布局布线后仿真"，也可以读成"至少要做到门级"。
   **两种读法的工作量差一个数量级，建议向组委会二次确认。** 在确认前，按"需要补一轮门级仿真"准备风险。
2. **评测用参赛者自己的 TB** —— 这是好消息：`sim/` 下的 56 项清单、回归脚本和 manifest 本身就是评分对象，
   现有"源版本 / 命令 / 配置 / 结果 / 覆盖边界"的记录纪律是加分项。但也意味着 **TB 的可读性与一键复现比通过率更重要**。
3. **不提供参考激励、不规定协议版本** —— 三次追问（SNMP 层级、615A 是否必须真 TFTP、RTC 同步范围）都被
   "建议参考协议规范" 挡回。**结论：协议子集由参赛者自定义，但必须在设计书里写明范围与依据。**
   项目现有做法（设计书 §2.2/§2.6 的 SNMP/615A 子集表）方向正确，**应再补一句"子集自界定"的声明**。

## 2. 选题一：接口与 MAC

| 问 | 答（原话） |
|---|---|
| 给 MAC 层的接口是 RGMII 还是 GMII？ | **GMII** |
| 参赛设计是否需要实现以太网 MAC（前导码、SFD、填充、FCS/CRC、IFG），还是只做 MAC 上层 AFDX 协议？ | **不需要实现以太网，可以调用 eLinx 工具里面的 IP。** |
| 顶层接口含义？是否可以增加新接口？tx_data/rx_data 是否用于传输完整以太网 MAC 帧？数据范围是否包括 Preamble/SFD/FCS/IFG？ | **顶层接口含义请参考接口信号的注释；参赛者可以酌情增加新的接口。**（**帧边界问题未正面回答**） |
| 握手关系确认：`tx_valid && rx_ready` / `rx_valid && tx_ready`？ | **ready 信号可以不用到。** |
| 能否提供 PCIe 相关 IP 或示例 Demo？eLinx 教育版里没找到。 | **目前没有相关的 IP 和 Demo 可以提供。** |

### 对本项目的影响

- **MAC 不是必做项**。项目当前自己实现了 MAC 侧逻辑（GMII/CRC32 等，见文献域 G 与 §8.1 CRC 展开）。
  这不违规，而且自实现更可控；但**如果综合/时序压力主要来自 MAC 部分，可以考虑换成 eLinx IP 换取收敛余量**——需要先有 post-fit 热点数据才谈得上。
- **`ready` 可以不用** → 顶层握手可简化为 valid-only，但项目现有背压语义（RX 查表 5 拍流水、块所有权）是内部设计，**不要因为这句话去动内部背压**。
- **Preamble/SFD/FCS/IFG 的帧边界始终没有明确答复**，这是选题一目前最大的接口口径风险。建议单独再问一次，
  并在设计书里显式写出本设计的假设（例如 tx_data 从 DA 起、不含 Preamble/SFD/FCS，IFG 由 MAC IP 保证）。

### 对本项目的影响

- **"不绑定器件型号，任意选择一款器件即可"** 直接改变了时序这条线的性质：
  现在用 **EP4SGX530（代理器件）** 出 post-fit **完全合规**，不再需要向赛方目标器件对齐。
  README 里"代理器件报告与赛方 eLinx 交付分开"的顾虑可以放松一档。
  **但这不等于 125 MHz 可以不收敛**——选器件是自由的，选完之后在该器件上收敛仍是自证质量的核心指标。
  也**不构成降频或放宽约束的理由**（项目自订纪律，优先级高于这条答复）。
- 赛方**没有明说要不要交综合/布局布线报告**。按"不交白不交"处理：现有 post-fit / STA 证据继续保留。
- 没有模板、没有技术指导、没有参考激励、没有 PCIe Demo —— **一切自证，文档链的完整性就是竞争力**。

## 4. 选题二：规则要点速查（仅记录）

| 项目 | 最终口径 |
|---|---|
| Yosys 版本 | 出题时按 0.68，后改为 **统一 0.69**（0.69 的 ABC 子模块对 MUX 树映射更好） |
| 综合命令 | **统一 `synth_intel`**；映射 `synth_intel -family cycloneiv` |
| 优化 pass 的位置 | 编译进 `synth_intel.cc` 内部调用；**禁止 `plugin -i` 加载 .so** |
| pass 顺序 | 在 `synth_intel` 组合命令集中自行调试确定位置，**结果最优即可** |
| ABC | 先答"可以调整 abc 脚本"，后**收紧为"请都用 yosys 自带的 abc9 运行，这个需要统一"**；调优较好的 abc 脚本需一并提交 |
| 基线臂 | 完全未修改的原版 yosys，**脚本逐字相同，只差二进制** |
| 用例 | **只以 QQ 群 4 个 case 为准**，不加更复杂的混合 case |
| 面积指标 | （优化前逻辑单元数 − 优化后）/ 优化前；**按每个用例分别算再平均**；**主看 LUT 逻辑单元**；DFF/IO 等**原则上不能增加** |
| PMUX 识别 | 若用例里识别不出 PMUX，**把其他逻辑合成 PMUX 再优化也可以——最终看网表结果** |
| 等价验证 | EQY，**在 abc 之后输出 ilang 验证 `$lut` 单元**（完全映射为 cycloneiv 单元后 EQY 不识别）；EQY 版本可另选；**允许切换整设计 miter 模式，算作通过** |
| 提交物 | ①优化源码（含新增 `opt_xxx.cc`，若改了 abc 脚本一并交） ②编译后的 yosys 二进制及其依赖库 |

## 5. 选题二：答复之间的矛盾（若要做选题二必须先澄清）

1. **时间开销**：
   先答"指标指的就是开销，**时间是 cpu 时间**"、"**cpu 时间包括 abc**"、评分细则写有 60 s / 2 GB 约束；
   后又答"**编译耗时并不作为评分选项**"。→ **直接冲突，需再确认。**
2. **内存口径**：
   先答"内存是**整个进程**的峰值"；后答"**峰值工作内存，只看 yosys.exe**"。→ 后者更窄，以后者为准但建议书面确认。
3. **ABC 可调范围**：
   先答"**可以调整 abc 的脚本**"；后答"请都用 yosys 自带的 **abc9**，这个需要统一"。
   → 可读为"映射器必须是 abc9，但 abc9 的脚本内容可调"。
4. **版本**：0.68 → 0.69 两次改口；且参赛者实测 **Windows `oss-cad-suite` 0.69 原版 `synth_intel -family cycloneiv` 的 abc9 在部分用例断言崩溃（`vecInt.h:446`）**，
   组委会对"基线跑不出来怎么办"**只回了 EQY 版本可换，没有正面回答**。→ 仍是开放风险。
5. **60 s / 2 GB 的绝对约束 vs "取相对量排除 PC 差异"**：
   最终答复是"case 规模不大，常规 PC 不应超过临界；**若原版超过则优化版超过也允许**"。

## 7. 建议向组委会二次确认的三个问题

1. **"综合后仿真即可"** 是"必须做到门级仿真"，还是"RTL 功能仿真 + 综合通过即可、不强制门级"？
   （直接决定要不要补一整轮门级 + SDF 回归）
2. **顶层 `tx_data/rx_data` 的帧边界**：是否包含 Preamble / SFD / FCS / IFG？从 DA 开始还是从 Preamble 开始？
3. **是否需要提交综合 / 布局布线 / 资源 / 时序报告**？既然不绑器件，这些报告是否计入评分？
