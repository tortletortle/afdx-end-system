# 时序违例族分析（Continue12 post-fit，2026-09-28）

**数据来源**：`out/arena-debug/continue12/sta_scan/setup_endpoints_full.rpt`
生成方式：不重跑 fit，仅用 `quartus_sta -t sta_scan3.tcl` 重报（40 s）——
`report_timing -setup -npaths 30000 -nworst 1 -less_than_slack 0 -detail summary`。
`-nworst 1` 表示每个终点只取最差一条路径，避免同一终点的数千条路径淹没统计。

**说明 30000 的上限未被触及，本表是全量违例，不是截断样本。**

## 3. 三条主线

### 3.1 配置 FF 阵列（`cfg_sch_base` + `tx_cfg_mem` + `port_w0_sh`）—— 合计 1 490 个终点，**20.7%**

这是**占比最大的可归因原因**，且与既有待办 **OPT-7（`tx_cfg_mem`/`port_cfg_mem` 由 FF 阵列改 BRAM）完全重合**。
FF 阵列的每一位都要扇出到 `u_sched` / `u_rxpb` / `u_txbuf` 的组合逻辑，形成大量中等深度路径——
正是「浅滩」形态的主要来源。

**行动**：OPT-7 从「资源优化」升级为 **时序收敛主线**。
方法依据见 L147（BRAM 读改写 2–3 拍延迟反而更易收敛）、L125–L127（多端口存储）、
L152 §6.1（物理综合 / 寄存器复制）。

### 3.2 SNMP 管理面 —— 1 204 个终点，16.8%，含全局最差路径

最差路径为 `snmp_lite|oid_len[3..5]` → `altsyncram vl_stat_mem|portb_address_reg0`。

**关键判断：这一族很可能不需要改 RTL，而是 SDC 缺失。**
SNMP 是低速管理面，OID 解析与统计表读取不可能每拍发生。
若 RTL 上确为使能门控的多拍操作，正确做法是加 `set_multicycle_path`，
**16.8% 的违例可以合法消失，且零 RTL 改动**。

⚠️ 前提：必须先用 RTL/波形证明该路径确实多拍有效，
**不得为了凑时序而加无依据的 multicycle/false path**——这属于伪造收敛。
同理适用于 `u_timebase ==> u_sched`（80）与 `g_rtc.u_rtc`（13）。

### 3.3 数据面 —— 约 434 个终点，6.0%

`u_rxprs ==> u_rxpb`（280）、`u_mac_rx_a/b` 内部（142）、`u_builder ==> u_mac_a`（7）、
`u_rxlookup ==> u_rxcfg_flt1`（5）。

占比虽小，但**这是唯一必须靠 RTL 流水化解决的部分**，无法用 SDC 绕开。
`u_rxprs → u_rxpb` 是其中最大的一条，值得优先看。

## 4. 建议顺序

1. **改 `sta_post_fit.tcl` 的 `-npaths 50` → `-npaths 2000 -nworst 1`**（立刻做，防止再误判）。
2. **核实 SNMP / RTC / timebase 路径是否真为多拍**；若是，补 SDC 并重报 —— 预期消去约 18%。
3. **推进 OPT-7**（配置表 BRAM 化）—— 预期消去约 21%，且与既有资源优化目标一致。
4. 前两步做完重报 STA，再决定数据面（`u_rxprs → u_rxpb`）是否需要插流水级。
5. 全程遵守：**任何收敛结论只能来自本项目 fit/STA 实测**，文献只提供方法。
